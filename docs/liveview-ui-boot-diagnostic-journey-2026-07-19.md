# 라이브뷰·UI 부팅 진단 여정

작성일: 2026-07-19  
대상 시스템: Nikon D810 + Opal + `remote-ui/0716-1.html`  
목적: UI 부팅과 라이브뷰에서 문제를 발견하고, 원인을 분리하고, 수정 후 실제 장비에서 검증한 과정을 기록한다.

---

## 1. 이 문서가 기록하는 것

이 문서는 최종 코드 설명서가 아니다.

정상적으로 보이지 않았던 현상에서 출발하여 다음 과정을 기록한다.

```text
증상
  ↓
사용자 조작과 백그라운드 동작 분리
  ↓
UI 상태·세션 상태·브리지 로그·PTP 응답 연결
  ↓
경쟁 프로세스와 시간축 확인
  ↓
최소 범위 수정
  ↓
오팔 배포
  ↓
제품 UI + 실제 카메라 검증
```

특히 중요한 원칙은 다음이다.

1. UI에 표시된 상태를 카메라의 실제 상태로 간주하지 않는다.
2. 사용자가 누른 버튼만 보지 않고, 백그라운드 프로세스까지 함께 본다.
3. “느리다”를 하나의 문제로 묶지 않고 구간별 시간으로 분해한다.
4. 기능 정상화와 성능 최적화를 같은 변경으로 섞지 않는다.
5. 수정 후에는 반드시 오팔의 제품 UI에서 다시 측정한다.

## 1.1 이 문서에서 말하는 사용자 관점의 안정성

이 프로젝트에서 안정성이란 프로세스가 살아 있거나 로그에 오류가 없다는
뜻만으로 정의하지 않는다.

> 사용자가 내부 세션, PTP, 워커, 락, 캐시, 리페어 모듈의 존재를 알지 못해도
> 화면을 열고 카메라를 조작하면 시스템이 예상한 결과를 일관되게 제공하는
> 상태를 안정 상태로 정의한다.

사용자는 현재 세션 번호, 워커 상태, 프레임 캐시 위치, PTP 응답 코드,
리페어 모듈의 동작 여부를 직접 확인하지 않아도 되어야 한다.

시스템은 다음을 보장해야 한다.

1. UI를 열면 카메라와 세션이 자동으로 준비된다.
2. LIVE를 누르면 라이브뷰가 시작되거나 이해 가능한 오류가 표시된다.
3. AF와 SHOT은 사용자의 요청 없이 실행되지 않는다.
4. 명령이 끝나면 일시 상태와 락이 정리된다.
5. 라이브뷰는 내부 경쟁 때문에 갑자기 멈추지 않는다.
6. 일시적인 연결 문제는 시스템이 자체적으로 복구한다.
7. 복구할 수 없는 문제만 사용자에게 명확히 알린다.

내부 로그가 깨끗해도 사용자가 새로고침을 반복하거나 세션 번호를 직접
확인해야 한다면 사용자 관점에서는 안정적이지 않다.

## 2. 기준 구조

현재 시스템의 실제 책임 경계는 다음과 같다.

```text
UI 부팅
  └─ session-manager
      ├─ 새 명령 세션 번호 발급
      ├─ bridge 상태 확인
      ├─ WebSocket 시작
      ├─ battery worker 시작
      └─ repair guard 시작

카메라 작업
  └─ d810bridge.lua
      ├─ ddserver PTP 연결
      ├─ 카메라 세션 유지
      ├─ AF / SHOT / LIVE 명령 처리
      ├─ live_session 고정
      └─ 프레임 캐시와 메타데이터 생성

프레임 전달
  └─ d810ws.lua
      ├─ 최신 meta 감시
      ├─ frameId 변화 확인
      └─ WebSocket meta + JPEG 전달

화면
  └─ 0716-1.html
      ├─ 상태 표시
      ├─ 명령 입력
      ├─ 최신 프레임 슬롯
      └─ 렌더 중인 프레임 이후 최신 프레임 표시
```

이 구조에서 카메라에 PTP 명령을 보내는 주체는 브리지 하나여야 한다.
WebSocket과 UI는 카메라 명령 생산자가 아니라 소비자다.

## 3. UI 부팅 문제의 출발점

초기 UI 부팅에서는 다음 상태가 서로 맞지 않는 경우가 있었다.

```text
Camera: Detecting / Connect
Session Condition: Preparing
Session: --- 또는 이전 세션
Battery: --%
```

잠시 후에는 다음처럼 바뀌었다.

```text
Camera: Connect
Session Condition: Ready
Session: 새 세션 번호
Battery: 실제 값
```

문제는 단순히 화면 전환이 느린 것이 아니었다.

- UI가 새로고침되었는데 이전 세션이 남아 있는 경우가 있었다.
- 부팅 중 상태 조회와 카메라 감지가 같은 PTP 연결에 들어갔다.
- 기존 라이브 요청, 리페어 플래그, 워커 PID가 새 부팅에 남을 수 있었다.
- 상태 조회가 카메라의 준비 상태를 다시 확인하면서 명령 실행과 경쟁할 수 있었다.
- UI는 `Preparing`을 표시하지만 실제로는 백엔드가 이미 다른 상태에 있을 수 있었다.

따라서 UI 부팅 문제는 UI 애니메이션 문제가 아니라 세션 초기화 순서와
상태 소유권 문제로 분류했다.

## 4. UI 부팅 진단 방법

부팅 문제를 볼 때 다음 네 가지 시간을 같이 기록한다.

| 구간 | 확인 대상 |
|---|---|
| UI 시간 | 페이지 로드, 상태 폴링, 사용자 입력 시각 |
| 세션 시간 | session-manager가 세션을 발급한 시각 |
| 브리지 시간 | bridge 시작, BOOT, STATUS 처리 시각 |
| 카메라 시간 | PTP 연결, Device Ready, 프로퍼티 조회 시각 |

그리고 다음 파일을 함께 확인한다.

```text
/tmp/d810-session-v21.state
/tmp/d810-session-v21.mode
/tmp/d810-live-v21.session
/tmp/d810-session.live
/tmp/d810-session.repair
/tmp/d810-live-v21-refresh.pid
/tmp/d810-bridge-v21.pid
/tmp/d810-ws-v21.pid
```

핵심은 파일 하나의 존재만 보는 것이 아니라, 파일의 생성 시각과 프로세스
상태를 함께 보는 것이다.

예를 들어 `frame-refresh` PID 파일이 있어도 프로세스가 죽어 있으면 stale
상태일 수 있다. 반대로 PID 파일이 없어도 다른 경로에서 워커가 실행 중일 수
있으므로 `ps`와 로그를 함께 확인해야 한다.

## 5. 새로고침과 세션 번호 문제

UI 새로고침은 기존 화면을 다시 그리는 것만으로 끝나면 안 된다.

새로고침 시 필요한 동작은 다음과 같다.

1. 새로운 명령 세션 번호 발급
2. 이전 명령 큐와 임시 락 제거
3. 이전 리페어 요청 제거
4. 보조 라이브 워커 정리
5. 브리지 상태 재확인
6. UI에 새 세션 번호 반영
7. 라이브 세션은 정책에 따라 고정 유지 또는 명시적 재시작

여기서 명령 세션과 라이브 세션을 분리했다.

- 명령 세션: 새로고침 때 새 번호를 받는다.
- 라이브 세션: `live_session`, ID 1로 고정한다.

이 분리를 하지 않으면 UI 새로고침 때마다 라이브 연결도 새로 만들어지고,
카메라의 라이브 상태와 화면 상태가 흔들릴 수 있다.

## 6. 016 세션: AF를 눌렀는데 Preparing으로 진입

### 6.1 최초 관찰

사용자는 세션 상태가 `Ready`인 상태에서 AF 버튼만 눌렀다.
그런데 UI는 `Preparing`으로 들어갔고, 명령 실행이 끝나지 않거나 오래 걸렸다.

처음에는 다음 가설이 자연스러웠다.

```text
사용자는 AF만 눌렀다
→ 라이브 프레임 요청은 없었다
→ 라이브뷰와 겹칠 수 없다
```

하지만 이 가설은 사용자 입력만 기준으로 한 것이었다.

### 6.2 전후 로그 연결

016 세션의 전후 관계를 연결하자 다음 구조가 보였다.

```text
UI AF 클릭
  ↓
브리지 AF 명령 진입
  ↓
카메라 명령 락 대기
  ↓
백그라운드 라이브 워커도 같은 카메라 큐 접근
  ↓
카메라 PTP 응답 지연
  ↓
UI timeout 또는 Preparing 장기 유지
  ↓
리페어 감시가 실패로 해석할 가능성
```

사용자가 라이브뷰를 요청하지 않았어도, 이전에 살아 있던 라이브 워커가
카메라에 계속 프레임을 요청하고 있었던 것이다.

### 6.3 확인된 원인

- UI 명령과 라이브 프레임 생산이 같은 카메라를 사용했다.
- 두 경로가 같은 실행 순서를 공유하지 않았다.
- 카메라 큐가 하나인데 생산자가 둘이었다.
- timeout은 실제 카메라 처리 시간보다 짧거나 경쟁 상황을 고려하지 못했다.
- 실패 후 락과 보조 상태가 즉시 정리되지 않을 수 있었다.

### 6.4 해결 원칙

처리 시간을 무작정 늘리는 것보다 먼저 다음을 적용했다.

1. 카메라별 작업을 단일 브리지 경로로 모은다.
2. AF·SHOT·LIVE 캡처가 동시에 PTP를 실행하지 않게 한다.
3. 명령 하나가 끝나면 락과 임시 상태를 정리한다.
4. timeout은 정상 처리 시간과 재시도 시간을 포함해 설정한다.
5. UI fallback이 별도 카메라 워커를 만들지 못하게 한다.

## 7. 027 세션: 시간이 줄었지만 AF는 실제로 실행되지 않음

027에서는 Preparing에 머무는 시간이 짧아졌다.
그러나 이것은 “AF가 성공했다”는 증거가 아니었다.

이 단계에서 문제를 두 개로 분리했다.

```text
상태 표시 문제
  └─ UI가 빠르게 Ready로 돌아오는가?

기능 실행 문제
  └─ 카메라가 실제 AF PTP 명령을 수행했는가?
```

카메라 기능 정상화의 기준을 화면 상태가 아니라 다음으로 변경했다.

- AF PTP 명령이 실제로 전송됐는가?
- 카메라 응답 코드가 성공인가?
- 실패했다면 `Device Busy`, `AF 불가`, `세션 미준비` 중 무엇인가?
- 명령 완료 후 카메라 상태가 다시 Ready인가?
- 라이브 프레임 루프가 명령 결과를 덮어쓰지 않았는가?

이 관점은 이후 LIVE_START 문제를 발견하는 기반이 되었다.

## 8. 라이브뷰 첫 프레임 문제

### 8.1 증상

LIVE 버튼을 눌렀을 때 UI가 `Preparing`에 머물거나,
세션 상태는 `Ready`인데 프레임과 FPS가 나오지 않는 상황이 있었다.

초기 로그에는 다음과 같은 응답이 반복되었다.

```text
capture_failed
live view frame unavailable
response=0x2001,0x2001,0x2001
data=16,12
```

이때는 첫 프레임 워밍업 시간이 부족하다는 가설을 세웠다.

### 8.2 워밍업 수정의 한계

LIVE_START 후 일정 시간 대기하고 첫 프레임을 다시 요청하는 로직을 추가했다.
첫 프레임이 계속 없으면 라이브뷰를 한 번 정지했다가 재시작하도록 했다.

그러나 이것만으로는 문제가 완전히 해결되지 않았다.

왜냐하면 카메라가 라이브뷰를 시작하지 않았는데도 브리지가 성공으로 기록하고
있었기 때문이다.

## 9. LIVE_START의 PTP 응답 판정 오류

### 9.1 로그에서 확인한 실제 순서

121 세션에서 LIVE_START 직후 로그를 전체 순서로 확인했다.

```text
LIVE_START begin
  ├─ GET_DEVICE_PROP_VALUE
  ├─ DEVICE_READY → 0x2001
  ├─ START_LIVE_VIEW(0x9201) → 0x2019
  ├─ DEVICE_READY → 0x2001
  └─ live_start done

첫 프레임
  └─ GET_LIVE_VIEW_IMAGE(0x9203) → 0xA00B
```

`0x2019`는 카메라가 바쁘다는 응답인데, 기존 코드는 `execute()`의 응답 코드를
확인하지 않고 `live_view_active=true`로 바꾸었다.

따라서 시스템은 다음과 같이 잘못된 상태가 되었다.

```text
실제 카메라: 라이브뷰 시작 실패
브리지: live_view_active=true
UI: Ready 또는 Preparing
프레임 루프: 실패한 카메라에 계속 GET 요청
```

### 9.2 해결

다음 규칙을 적용했다.

- `0x2019`를 `RESP_DEVICE_BUSY`로 명시한다.
- Device Ready 응답을 확인한다.
- LIVE_START 응답을 확인한다.
- Busy이면 제한된 횟수만 재시도한다.
- 성공하기 전에는 라이브 활성 상태를 기록하지 않는다.
- 반복 실패 시 `liveview_start_failed`로 명확히 종료한다.

이 수정 후 LIVE_START는 “명령을 받았다”가 아니라 “카메라가 실제로 시작했다”
는 기준으로 성공하게 되었다.

## 10. 중복 라이브 워커 발견

### 10.1 예상하지 않은 라이브뷰

사용자가 LIVE를 누르지 않았는데 카메라 프레임 요청이 나타나는 이유를
추적하면서 `frame-refresh-v21` 워커를 확인했다.

초기 fallback 흐름은 다음과 같았다.

```text
WebSocket 연결 실패
  ↓
UI가 live-fallback 호출
  ↓
action-v21이 frame-refresh-v21 시작
  ↓
워커가 FRAME_STORE 요청
  ↓
브리지도 자체 백그라운드 캡처를 수행
```

라이브뷰가 실패했을 때 복구하려던 코드가 오히려 카메라의 두 번째 생산자가
되었다.

### 10.2 워커와 브리지의 상호 차단

브리지에는 워커 PID 파일이 있으면 자체 백그라운드 캡처를 하지 않는 조건이
있었다.

그래서 다음과 같은 교착성 흐름이 가능했다.

```text
UI가 fallback 워커 시작
  ↓
브리지가 PID 파일을 보고 자체 캡처 중지
  ↓
fallback 워커가 FRAME_STORE 요청
  ↓
카메라 응답 실패 또는 세션 락 대기
  ↓
프레임 없음
  ↓
리페어 요청 생성
```

### 10.3 해결

- 브리지를 유일한 라이브 프레임 생산자로 고정했다.
- `live-fallback`은 카메라 캡처 워커를 시작하지 않는다.
- fallback은 브리지 캐시를 소비하는 상태만 반환한다.
- LIVE_ON 시 stale `frame-refresh` 워커를 먼저 정리한다.
- 브리지는 PID 파일 때문에 자체 생산을 중단하지 않는다.
- `frame-refresh` 프로세스가 실제로 없는지 제품 테스트에서 확인한다.

## 11. 메타데이터 누락 문제

### 11.1 발견

JPEG 파일은 갱신되고 있었지만 `/tmp/d810-live-v21.meta`는 0바이트였다.

이 상태에서는 WebSocket이 새 프레임을 정확히 알 수 없었다.

기존 fallback은 다음을 비교했다.

- JPEG 파일 크기
- 파일 앞부분 바이트
- 파일 뒷부분 바이트

하지만 연속 프레임의 JPEG 크기가 같을 수 있기 때문에 새 프레임을 놓칠 수
있었다.

### 11.2 코드 원인

`_capture_frame()`은 내부에서 `self.last_metrics`를 만들었지만,
백그라운드 호출부가 다음처럼 프레임만 받았다.

```lua
local frame, frame_meta = self:_capture_frame(false)
write_frame_cache(frame, frame_meta)
```

반환 계약이 실제 사용 방식과 맞지 않아 `frame_meta`가 비어 있었다.

### 11.3 해결

- 프레임과 메타데이터를 함께 반환한다.
- 오류 캐시 경로도 메타데이터를 함께 반환한다.
- 메타데이터를 임시 파일에 기록한 뒤 `rename`으로 교체한다.
- WebSocket이 `frameId`를 기준으로 새 프레임을 판정한다.

이 수정은 단순히 로그를 풍부하게 한 것이 아니다.
프레임 전달 경로가 “추측”에서 “생산자가 부여한 순번” 기반으로 바뀌었다.

## 12. FPS 저하의 구간별 진단

### 12.1 수정 전 계측

제품 UI에서 라이브뷰는 약 10.5 FPS였다.

브리지 메타에서 확인한 값은 다음과 같았다.

```text
captureMs: 23–29ms
cacheMs: 2–3ms
requestGapMs: 71–75ms
```

카메라 캡처와 캐시 기록이 전체 지연을 설명하지 못했다.
따라서 남은 71–75ms를 브리지 루프와 락 처리로 좁혔다.

### 12.2 불필요한 프레임별 락

라이브 프레임 하나를 생산할 때 다음 파일시스템 작업이 반복되었다.

```text
FRAME_CAPTURE_LOCK 생성
COMMAND_ACTION_LOCK 생성
PTP 프레임 획득
JPEG·메타 기록
COMMAND_ACTION_LOCK 제거
FRAME_CAPTURE_LOCK 제거
```

이 시스템은 브리지 하나의 이벤트 루프가 카메라 작업을 이미 직렬 처리하고
있었다. 따라서 라이브 백그라운드 루프에서 외부 프로세스 기반 락을 매번
만드는 것은 중복이었다.

### 12.3 수정 후 계측

백그라운드 프레임 캡처에만 중복 프로세스 락을 생략했다.

그 결과:

```text
requestGapMs: 약 71–75ms → 약 8ms
브리지 생산: 8초 동안 213프레임
브리지 생산량: 약 26.5 FPS
UI 표시: 24.4–24.6 FPS
```

실제 개선의 핵심은 쓰기를 더 빠르게 만든 것이 아니라, 프레임마다 반복되던
불필요한 락 파일 생성·삭제와 셸 프로세스 실행을 제거한 것이다.

## 13. 최종 UI 프레임 경로

현재 UI는 프레임을 모두 쌓아두지 않는다.

```text
카메라 프레임 생산
  ↓
브리지 frameId 부여
  ↓
JPEG + meta 기록
  ↓
WebSocket 최신 frameId 감시
  ↓
UI 수신
  ↓
렌더 중이면 pending 슬롯에 최신 프레임만 보관
  ↓
렌더 완료 후 최신 프레임 표시
```

이 정책은 프레임을 일부 건너뛸 수 있다.
그러나 사용자가 보는 화면의 지연이 계속 누적되지 않고, 현재 시점에 가까운
프레임이 표시된다.

제품의 목표가 카메라의 모든 프레임을 분석용으로 보존하는 것이 아니라,
UI에서 물 흐르듯 보이는 영상이라면 이 정책이 맞다.

## 14. 문제 발견·해결의 판정 기준

### 문제라고 판정하는 경우

- 사용자 입력 없이 LIVE_START 또는 FRAME_STORE가 반복된다.
- `Ready`인데 실제 PTP 응답이 `Device Busy`다.
- FPS가 낮은데 `captureMs`가 아니라 `requestGapMs`가 크다.
- meta가 비어 있고 JPEG만 갱신된다.
- `frame-refresh` PID가 라이브뷰 중 존재한다.
- UI 세션 번호와 브리지 세션 번호가 다르다.
- 리페어 파일 생성이 반복된다.
- 새로고침 후 이전 세션의 라이브 상태가 섞인다.

### 해결됐다고 판정하는 경우

- 원인 코드와 로그 순서가 설명된다.
- 수정 후 같은 조건에서 수치가 개선된다.
- 기능 응답 코드가 실제 카메라 응답과 일치한다.
- 단일 생산자 조건이 유지된다.
- 리페어가 불필요하게 개입하지 않는다.
- AF·SHOT·STOP이 라이브뷰를 불필요하게 망가뜨리지 않는다.
- 일정 시간 지속 테스트에서 세션 교체나 stale 워커가 없다.

## 16. 현재 남은 경계와 주의점

24 FPS가 확인됐다고 해서 모든 상황에서 24 FPS가 보장되는 것은 아니다.

- AF 실행 중에는 카메라가 잠시 Busy가 될 수 있다.
- SHOT은 라이브 캡처와 같은 카메라 자원을 사용한다.
- USB/PTP 연결 상태가 변하면 카메라 생산량이 내려갈 수 있다.
- 장시간 운용에서는 배터리와 ddserver 상태를 별도로 봐야 한다.
- 직접 소켓 스트림을 다시 도입하면 브리지 write가 PTP를 막지 않는지 재검증해야 한다.
- 성능 목표를 더 높이려면 FPS보다 p95 latency와 명령 응답성을 먼저 측정해야 한다.

현재 안정성 기준선은 다음과 같이 고정한다.

```text
목표 기준: 15 FPS
실제 UI 기준선: 약 24 FPS
실제 브리지 생산 기준선: 약 26 FPS
```

문제를 다음과 같이 올바르게 분리한 것이 핵심이었다.

```text
UI 표시 문제
≠
세션 부팅 문제
≠
카메라 PTP 시작 문제
≠
프레임 생산 문제
≠
메타데이터 전달 문제
≠
렌더링 문제
```

016과 027에서는 명령과 라이브뷰의 충돌 및 상태 판정 문제를 확인했고,
이후 라이브뷰에서는 `Device Busy` 성공 오판, 중복 생산자, 메타데이터 누락,
프레임별 셸 락 비용을 단계적으로 확인했다.

최종적으로 브리지를 단일 카메라 생산자이자 상태 중심으로 만들고,
WebSocket과 UI를 소비자 역할로 제한했다. 그 결과 실제 제품 UI에서 약 24 FPS,
카메라 생산 약 26 FPS를 확인했다.

이 기록은 앞으로의 Semi OS 개발에서 다음 질문을 유지하기 위한 기준이다.

> 문제가 발생했을 때, 누가 카메라를 만졌고, 어떤 응답을 받았으며,
> 어느 구간에서 시간이 사라졌고, 왜 리페어가 개입했는가?

## 19. 현재 실사용 가능성 판정

현재 상태는 **실제 장비를 연결한 감독형 실사용 테스트에는 진입 가능하지만,
사용자가 내부 상태를 전혀 신경 쓰지 않아도 되는 완전한 무감독 실사용으로
확정하기에는 검증이 더 필요하다.**

현재 확인된 강점:

- UI 부팅 후 새 명령 세션이 만들어진다.
- LIVE_START의 실제 카메라 응답을 확인한다.
- 라이브뷰가 제품 UI에서 약 24 FPS로 동작한다.
- 카메라 생산량 약 26.5 FPS와 UI 표시량 약 24.6 FPS를 확인했다.
- 단일 라이브 생산자 구조가 유지된다.
- 메타데이터와 frameId로 프레임 신선도를 판정한다.
- 확인한 8초 구간에서 리페어 요청과 stale 워커가 없었다.

아직 완전한 무감독 안정성으로 확정하지 않은 이유:

- 8초 성능 검증은 장시간 운용 검증이 아니다.
- 라이브 중 AF·SHOT을 반복하는 장시간 시나리오가 더 필요하다.
- USB 분리·재연결, 카메라 전원 변화, 배터리 부족 상황을 모두 통과했다는
  증거가 부족하다.
- 리페어 모듈의 반복 실패·재시작 예산을 장시간 확인해야 한다.
- 네트워크 단절 후 사용자 개입 없이 정상 화면으로 돌아오는지 추가 검증이
  필요하다.

따라서 현재의 정확한 표현은 다음과 같다.

```text
라이브뷰: 실사용 테스트 가능
UI 부팅: 정상화된 기준 경로 확보
AF·SHOT: 기능별 반복 검증 필요
리페어: 구조와 관측계 확보, 장시간 검증 필요
전체 제품: 감독형 실사용 가능, 무감독 안정성은 미확정
```
