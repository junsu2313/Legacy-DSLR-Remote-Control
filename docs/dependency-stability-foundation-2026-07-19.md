# 개발 안정성 기반선: 의존성 단순화와 실사용 복구력

작성일: 2026-07-19
버전: 1.0 Alpha
목적: 기능 추가 전에 실행 주체와 의존성을 줄이고, 사용자가 새로고침하지 않아도 런타임이 복구되는 기반을 고정한다.

## 적용 범위

이번 단계에서는 의존성·실행 주체 전수 조사, 카메라 생산자 단일화 확인,
브리지·WebSocket·리페어 감시자 통합, 중복 배터리 워커 방어, UI 부팅 후
자동 복구 경로 확보, WebSocket 장애와 브리지 장애 실기 검증을 진행했다.

세션 수명주기의 최종 정의는 이번 단계에서 확정하지 않는다.

## 다음 배포 예정 기능

기능 추가 전 선행 기반 작업은 세션을 새로 만들지 않고 내부 구성요소를 먼저
복구하는 세션 유지·복구 구조다. 세션 재생성은 PTP 세션 손실·카메라 재연결·
복구 한도 초과처럼 기존 세션을 보존할 수 없을 때만 마지막 수단으로 사용한다.

`개발 예정 기능 1`은 NX Studio 방식의 필름 시뮬레이션과 원본 보존이다.
`개발 예정 기능 2`는 라이브뷰를 유지한 채 AF와 SHOT을 각각 독립적으로
실행할 수 있는 가능성을 검증하는 기능이다. AF 버튼은 AF만 실행하고,
SHOT은 별도 사용자 입력으로만 실행한다. 현재 배포본은 안전성을 위해
AF·SHOT 전에 라이브뷰를 종료하므로, 이 기능은 로컬에서 먼저 구현·검증하고
실제 카메라 반복 테스트 후 다음 배포에 포함한다.

## 사용자 관점의 안정성 정의

> 사용자가 세션 번호, PTP, 워커, 락, 캐시, 리페어 모듈의 존재를 알지 못해도
> UI를 열고 카메라를 조작하면 시스템이 예상한 결과를 일관되게 제공하는 상태를
> 사용자 관점의 안정 상태로 정의한다.

안정성은 UI 자동 부팅, 무새로고침 장애 복구, 사용자 요청 없는 명령 방지,
실패 후 내부 상태 정리, 단일 PTP 생산자를 포함한다.

## 이전 실행 구조의 문제

기존에는 `session-manager`의 inline repair guard, `session-health`,
`stack-guardian`, WebSocket, `battery-worker`, bridge가 함께 존재했고,
UI fallback은 `frame-refresh-v21`을 시작할 수 있었다.

문제는 모듈 수보다 책임이 겹친다는 점이었다.

- `session-health`와 `stack-guardian`은 반복 감시자가 아니라 일회성 실행에 가까웠다.
- 리페어 감시는 `session-manager` 내부 서브셸로 별도 존재했다.
- `frame-refresh-v21`은 fallback 상황에서 두 번째 PTP 생산자가 될 수 있었다.
- `battery-worker`는 PID 하나만 보고 중복 실행을 정상으로 판단할 수 있었다.

## 현재의 단순화된 실행 구조

```text
session-manager
  ├─ bridge
  ├─ d810ws
  ├─ battery-worker
  └─ runtime-guardian

runtime-guardian
  ├─ bridge 생존 감시
  ├─ bridge BOOT 복구
  ├─ WebSocket 재시작
  ├─ battery-worker 중복·소실 감시
  └─ SESSION_REPAIR_REQUEST 처리

bridge
  └─ 유일한 카메라 PTP 생산자

UI
  └─ 명령 요청·최신 프레임 소비자
```

### 실행 주체 계약

| 주체 | 할 수 있는 일 | 하면 안 되는 일 |
|---|---|---|
| `session-manager` | 부팅·정리·런타임 시작 | 프레임을 직접 캡처하지 않음 |
| `runtime-guardian` | 프로세스·복구 감시 | 프레임을 직접 캡처하지 않음 |
| `d810bridge` | 모든 카메라 PTP 작업 | 다른 PTP 생산자를 만들지 않음 |
| `d810ws` | 캐시 프레임 전달 | 카메라 명령을 보내지 않음 |
| `battery-worker` | 유휴 배터리 조회 | 라이브 중 카메라를 만지지 않음 |
| UI | 사용자 명령·최신 프레임 표시 | fallback 워커 생성·PTP 판단을 하지 않음 |

## runtime-guardian 동작

guardian은 2초 주기로 브리지 PING, 브리지 장애 시 BOOT, 라이브 상태 복원,
WebSocket 생존, 배터리 워커 생존·중복, 리페어 요청을 확인한다.

guardian은 정상 프레임을 직접 요청하지 않는다. 복구 감시가 라이브뷰 생산
경로를 다시 막지 않도록 하는 것이 핵심이다.

## 중복 워커 방어

실제 적용 직후 `battery-worker`가 여러 개 남아 있는 상태가 발견됐다.
기존 `battery_worker_alive()`는 PID 파일의 한 PID만 확인했다.

현재는 실행 중인 워커 수를 계산하고, 2개 이상이면 전체를 정리한 뒤 guardian이
단일 워커를 다시 시작한다.

실제 검증에서는 8개의 중복 워커를 정리한 뒤 다음 상태로 수렴했다.

```text
battery-worker: 1
runtime-guardian: 1
d810bridge: 1
d810ws: 1
frame-refresh-v21: 0
```

## 자동 복구 실기 검증

### WebSocket 장애

WebSocket 프로세스를 의도적으로 종료했다.

- guardian이 새 WebSocket을 시작했다.
- 사용자가 UI를 새로고침하지 않았다.
- UI는 `Ready`를 유지했다.
- UI FPS는 `22.6 FPS`로 복귀했다.
- 프레임 meta는 계속 갱신됐다.

### 브리지 장애

브리지 프로세스를 의도적으로 종료했다.

- guardian이 브리지를 다시 시작했다.
- BOOT을 수행했다.
- 라이브 상태를 복구했다.
- 사용자가 UI를 새로고침하지 않았다.
- UI는 `Ready / 23.0 FPS / 28ms`로 복귀했다.
- 명령 세션은 `132_session`으로 유지됐다.

이 검증은 장애가 발생하지 않는다는 뜻이 아니라, 장애가 발생해도 사용자가
내부 상태를 조작하지 않고 복구된다는 뜻이다.

## 보류한 항목

세션 수명주기의 최종 정의는 보류한다.

- 명령 세션과 라이브 세션을 언제 같은 런타임으로 볼 것인가?
- UI 새로고침 중 라이브 연결을 항상 보존할 것인가?
- 카메라 재연결 시 라이브 세션 ID를 유지할 것인가?
- 장시간 장애 후 새 명령 세션을 발급하는 기준은 무엇인가?

이 질문은 상태 전이표를 먼저 작성한 뒤 별도 작업으로 확정한다.

## 다음 기능 추가 규칙

1. 카메라에 직접 연결하지 않고 bridge command를 사용한다.
2. 새 백그라운드 워커를 만들기 전에 guardian과 책임 관계를 정의한다.
3. 상태 조회와 실행 명령을 같은 함수에서 처리하지 않는다.
4. 새로운 캐시는 소유자·수명·삭제 시점을 명시한다.
5. 실패 시 리페어 요청인지 사용자 오류인지 명시한다.
6. 기능 추가 후 단일 생산자·워커 수·세션 상태를 회귀 확인한다.
7. Opal 제품 UI에서 부팅·LIVE·STOP·장애 복구를 다시 검증한다.
