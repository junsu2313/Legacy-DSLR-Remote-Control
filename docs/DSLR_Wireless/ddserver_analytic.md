# ddserver Analytic

Recorded at: `2026-06-25 23:52:15 +09:00`

The `DslrDashboardServer` source was cloned locally into:

```text
_tmp_ddserver
```

Source size is small:

- `src/communicator.cpp`: main USB/PTP bridge implementation.
- `src/main.cpp`: TCP server and UDP discovery.
- `src/communicator.h`: packet structures and USB state.
- Total `src` file size: about 46 KB.

## Network Layer

`ddserver` listens on:

```text
TCP 4757
UDP 4757 multicast group 224.1.2.3
```

The UDP side is for discovery:

```text
DslrDashboardClient -> multicast query
DslrDashboardServer -> multicast response
```

The TCP side accepts client connections and creates one `Communicator` per client.

## Welcome Message

When a TCP client connects, ddserver sends a welcome message containing:

```text
DDS major version
DDS minor version
name = DslrDashboardServer
```

The current constants are:

```text
DDS_MAJOR = 1
DDS_MINOR = 1
DDS_NAME  = DslrDashboardServer
```

## Packet Shape

ddserver wraps packets with a 4-byte total packet size, then uses a PTP-like header:

```cpp
struct PtpPacket {
    uint32_t packet_len;
    uint16_t packet_type;
    uint16_t packet_command;
    uint32_t session_ID;
};
```

Important local commands handled by ddserver:

```text
0x0001  Open/select USB imaging device by vendor/product ID
0x0002  Return USB imaging device list
0x0003  Close socket
0x0004  Request interrupt packet
default Forward packet to USB device
```

This confirms that ddserver is mostly a PTP bridge, not a high-level camera API.

## USB Layer

ddserver uses `libusb`.

It looks for USB interfaces with:

```text
bInterfaceClass == 6
```

This is the USB still imaging class.

When opening the camera, it:

- Opens the USB device.
- Reads config descriptors.
- Finds bulk read/write endpoints.
- Finds interrupt endpoint.
- Detaches kernel driver if needed.
- Claims the imaging interface.

The code path is centered in:

```text
Communicator::openUsbDevice
Communicator::initUsbDevice
Communicator::claimInterface
```

## PTP Forwarding

For ordinary packets, ddserver does not interpret Nikon commands.

It forwards the client packet to USB:

```text
TCP client packet
  -> libusb bulk write
  -> camera
```

Then it reads the camera response:

```text
camera
  -> libusb bulk read
  -> TCP client response
```

This means Nikon-specific decisions such as:

```text
StartLiveView 0x9201
GetLiveViewImage 0x9203
EndLiveView 0x9202
```

must be generated by the client/adapter layer, not by ddserver itself.

## Important Consequence

ddserver can reduce our low-level burden, but it does not remove the need for a camera-command brain.

The likely final architecture remains:

```text
D810
  -> ddserver: USB/PTP transport
  -> adapter: Nikon command sequencing and HTTP/WebSocket API
  -> browser UI
```

The adapter needs to speak the ddserver TCP packet protocol and generate Nikon PTP commands.

## Why This Still Helps

Even if we must write the adapter, ddserver handles the fragile layer:

- USB device enumeration.
- USB interface claim/release.
- Bulk/interrupt endpoint selection.
- Packet transport between TCP and USB.
- OpenWrt daemon packaging.

That is a meaningful reduction in scope.

Without ddserver, we would need to implement both:

```text
USB/PTP transport + Nikon command logic
```

With ddserver, we focus on:

```text
Nikon command logic + browser-facing API
```

This keeps the project closer to a usable wireless D810 platform and farther from a full USB driver project.
