# D810 라이브뷰·기능 정상화·Semi OS 운영 기록

작성일: 2026-07-19  
버전: 1.0 Alpha  
대상 장비: Nikon D810  
대상 런타임: Opal `192.168.8.1`  
현재 UI: `/www/remote-ui/0716-1.html`  
현재 기준 세션: `125_session`  

## 1. 문서의 목적

이 문서는 단순한 최적화 결과가 아니라, 카메라 제어 시스템을 어떻게 관찰하고,
문제를 발견하고, 원인을 분리하고, 수정하고, 실제 장비에서 다시 검증했는지를
운영 기준으로 고정한다.

앞으로 같은 문제가 재발했을 때 다음 질문에 답할 수 있어야 한다.

1. 사용자가 누른 명령은 무엇이었는가?
2. 카메라에 실제로 어떤 PTP 명령이 들어갔는가?
3. 어느 세션과 어느 프로세스가 명령을 처리했는가?
4. 라이브뷰 프레임은 어느 구간에서 지연되거나 사라졌는가?
5. 상태 표시는 실제 카메라 상태와 일치했는가?
6. 리페어 모듈이 개입했다면 무엇을 근거로 개입했는가?
7. 수정 후 같은 증상이 사라졌다는 것을 어떤 수치로 확인했는가?

## 2. 현재 결론

현재 시스템은 라이브뷰와 명령 실행을 분리하되, 카메라에 들어가는 PTP 작업은
브리지 단일 실행 루프에서 직렬화하는 구조로 정상화되어 있다.

제품 UI를 실제 카메라에 연결한 상태에서 확인된 기준값은 다음과 같다.

| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| UI 라이브뷰 FPS | 약 10.5 FPS | 약 24.6 FPS |
| UI 지연 | 약 30ms | 약 25ms |
| 카메라 프레임 생산 | 약 11 FPS 수준 | 8초간 213프레임, 약 26.5 FPS |
| 카메라 캡처 시간 | 23–39ms 범위 | 23–39ms 범위 |
| 캐시 기록 시간 | 약 2–3ms | 약 2–3ms |
| 보조 `frame-refresh` 워커 | 재생성됨 | 미실행 |
| 리페어 요청 파일 | 생성됨 | 없음 |
| 세션 오류 | 재연결·준비 상태 흔들림 | `Ready`, `lastError=` 공란 |

현재 성능 하락은 해결 불가능한 한계가 아니라, 경로 중간의 불필요한 작업을
제거하면 크게 개선되는 문제였음이 확인되었다. 15 FPS 목표는 이미 넘었고,
현재 수치는 UI에서 연속 영상처럼 보이게 하는 요구에도 충분한 수준이다.

## 2.1 사용자 관점의 안정성 정의

이 프로젝트에서 안정성이란 프로세스가 살아 있거나 내부 로그에 오류가 없다는
뜻만으로 정의하지 않는다.

> 사용자가 세션 번호, PTP, 워커, 락, 캐시, 리페어 모듈의 존재를 알지 못해도
> UI를 열고 카메라를 조작하면 시스템이 예상한 결과를 일관되게 제공하는 상태를
> 사용자 관점의 안정 상태로 정의한다.

따라서 다음 조건을 만족해야 한다.

1. UI를 열면 카메라와 세션이 자동으로 준비된다.
2. LIVE를 누르면 라이브뷰가 시작되거나 이해 가능한 오류가 표시된다.
3. AF와 SHOT은 사용자의 요청 없이 실행되지 않는다.
4. 명령이 끝나면 락·큐·임시 상태가 정리된다.
5. 라이브뷰가 내부 경쟁 때문에 갑자기 멈추지 않는다.
6. 일시적인 연결 문제는 시스템이 자체적으로 복구한다.
7. 복구할 수 없는 문제만 사용자에게 명확히 알린다.

현재 판정은 `감독형 실사용 가능`이다. 라이브뷰는 제품 UI에서 약 24 FPS,
브리지는 약 26.5 FPS를 실제 카메라로 확인했고 단일 생산자와 관측계도 확보했다.
다만 장시간 운용, USB 분리·재연결, 배터리 부족, 라이브 중 AF·SHOT 반복,
네트워크 단절 후 무인 복구는 추가 검증이 필요하므로 `완전한 무감독 실사용`으로
확정하지 않는다.

## 3. Semi OS의 의미

여기서 말하는 Semi OS는 카메라 내부 펌웨어를 대체한다는 뜻이 아니다.
카메라와 USB/PTP 계층 위에 올라가서 다음을 담당하는 경량 운영 계층을 뜻한다.

```text
Nikon D810
  └─ ddserver: USB/PTP 저수준 전송
      └─ d810bridge: 세션·명령·라이브뷰·상태·복구 오케스트레이션
          ├─ command plane: AF / SHOT / 상태 명령
          ├─ live plane: 고정 라이브 세션과 프레임 생산
          ├─ observation plane: 로그·메타·상태·성능 측정
          ├─ repair plane: 재연결·복구·리페어 판단
          └─ UI plane: 표시·입력·최신 프레임 소비
```

Semi OS의 핵심은 기능을 많이 넣는 것이 아니라, 각 기능이 어느 층에 속하는지
명확하게 하여 서로의 책임을 침범하지 않게 하는 것이다.

## 4. 책임 경계

### 4.1 ddserver

- USB 장치와 PTP 전송을 담당한다.
- 컨테이너, 응답 코드, 데이터 패킷을 전달한다.
- UI 상태나 복구 정책을 판단하지 않는다.
- 이 계층은 가능한 한 안정적으로 유지하고, 성능 문제는 상위 경로에서 먼저
  측정한다.

### 4.2 d810bridge

- 카메라 세션을 소유한다.
- PTP 명령의 실제 순서를 결정한다.
- 라이브뷰 시작·정지와 프레임 획득을 담당한다.
- 상태와 성능 메타데이터를 저장한다.
- 복구 가능 여부와 리페어 요청을 판단한다.
- UI가 카메라에 직접 판단을 내리지 못하도록 중간 경계를 제공한다.

주요 파일:

- `remote-ui/cgi-bin/d810bridge.lua`
- `remote-ui/cgi-bin/bridge-common.sh`
- `remote-ui/cgi-bin/session-manager`
- `remote-ui/cgi-bin/variant-v21-env.sh`

### 4.3 WebSocket / 캐시 소비 계층

- 브리지가 생산한 프레임을 UI로 전달한다.
- 프레임을 카메라에 다시 요청하지 않는다.
- 메타데이터의 `frameId`를 기준으로 새 프레임을 판단한다.
- 프레임 렌더링이 느리면 최신 프레임으로 교체한다.
- 오래된 프레임을 쌓아 지연을 누적하지 않는다.

### 4.4 UI

- 사용자의 AF, SHOT, LIVE, STOP 입력을 전달한다.
- 상태와 오류를 표시한다.
- 카메라의 실제 상태를 추측하여 명령을 재생성하지 않는다.
- 라이브뷰에서는 모든 프레임을 보존하려고 대기하지 않고 최신 프레임을 즉시
  렌더링한다.

## 5. 세션 모델

### 5.1 명령 세션

새로고침·하드 리셋·재기동 시 새로운 번호를 부여한다.

- 예: `016_session`, `027_session`, `119_session`, `121_session`, `125_session`
- 명령 세션은 AF, SHOT, 상태 조회, 복구의 작업 문맥이다.
- 세션 번호는 진단 로그를 분리하기 위한 식별자다.
- 정상적인 UI 새로고침에서는 새 명령 세션으로 시작해야 한다.

### 5.2 라이브 세션

웹 사용 중 라이브뷰는 명령 세션과 별도로 유지하지만, 새 브라우저 세션 부팅 시에는
이전 라이브 세션을 재활용하지 않고 깨끗하게 초기화한다.

- `liveSessionId=1`
- `liveSessionLabel=live_session`
- 라이브뷰의 연결 자체는 매 프레임 또는 매 명령마다 새로 만들지 않는다.
- 명령 세션 교체가 라이브 스트림의 생산자를 교체하는 원인이 되어서는 안 된다.

### 5.3 세션 불변 조건

다음 조건이 깨지면 성능 최적화보다 먼저 세션 구조를 조사한다.

1. 라이브뷰 실행 중 `frame-refresh` 워커가 새로 생긴다.
2. 한 카메라에 둘 이상의 PTP 생산자가 생긴다.
3. LIVE_START 없이 백그라운드 캡처가 시작된다.
4. 세션 상태가 `Ready`인데 실제 카메라 응답이 `Device Busy`다.
5. UI가 이전 세션의 프레임을 새 세션의 상태로 표시한다.

## 6. 문제 발견에서 해결까지의 기록

### 6.1 016 세션: AF와 라이브뷰 간섭 의심

초기 증상은 세션 상태가 `Ready`인 상태에서 AF를 눌렀을 때 `Preparing`으로
들어가고 명령 실행이 끝나지 않는 현상이었다.

처음에는 사용자가 라이브 프레임을 요청하지 않았으므로 AF와 라이브뷰가 겹칠
이유가 없다고 판단했다. 로그를 전후 관계로 연결한 결과, UI의 직접 입력 외에
백그라운드 라이브뷰 워커가 살아 있었고, 카메라 명령 락을 점유한 상태에서
AF가 같은 장치로 진입하려는 구조가 확인되었다.

핵심 교훈:

- “사용자가 누른 버튼”만으로 카메라 입력을 추정하면 안 된다.
- 백그라운드 프로세스와 자동 복구 프로세스까지 같은 시간축에 놓고 봐야 한다.
- 카메라별 단일 명령 큐와 직렬 실행이 필요하다.
- 타임아웃을 늘리는 것은 보조 수단이며, 먼저 처리 경로와 경쟁자를 줄여야 한다.

### 6.2 027 세션: 시간은 줄었지만 AF가 실제로 실행되지 않음

027 세션에서는 AF 버튼을 눌렀을 때 `Preparing`에 머무는 시간이 줄어들었다.
그러나 실제 카메라가 AF를 수행했는지는 확인되지 않았다.

이때 상태 표시 개선만으로는 충분하지 않다는 점을 확정했다.

- UI 상태 변화는 명령 수락과 동일하지 않다.
- 브리지 응답이 성공이어도 PTP 응답 코드가 성공인지 확인해야 한다.
- “AF 불가”, “카메라 비지”, “세션 미준비”는 서로 다른 결과로 표시해야 한다.
- 명령 하나가 끝난 뒤 락, 큐, 임시 상태, 리페어 플래그를 정리해야 한다.

### 6.3 초기 라이브뷰 경로: 낮은 FPS와 중복 생산자

초기 라이브뷰는 기능적으로 프레임이 나왔지만 UI FPS가 약 10 FPS 수준으로
낮았다. 카메라에 프레임을 요청하고, 파일에 쓰고, WebSocket이 다시 읽고,
UI가 디코드·렌더링하는 여러 단계가 겹쳐 있었다.

이 과정에서 다음 구조적 문제가 드러났다.

- 브리지의 백그라운드 캡처 루프
- 실패 시 UI가 시작하는 `frame-refresh-v21` 워커
- 파일 캐시를 감시하는 WebSocket
- 이전 직접 스트림 연결의 잔여 소켓
- 리페어 플래그를 감시하는 세션 매니저

즉, 라이브뷰 생산자가 하나가 아니라 상황에 따라 둘 이상이 될 수 있었다.
워커가 브리지의 자체 캡처를 막거나, 워커가 다시 브리지에 `FRAME_STORE`를
요청하면서 카메라 큐를 경쟁하는 구조였다.

### 6.4 메타데이터 공백 문제

브리지의 `_capture_frame()`은 `self.last_metrics`를 만들고 있었지만,
`capture_live_frame_background()`가 반환값을 프레임 하나로만 처리하여
`frame_meta`가 비어 있었다.

그 결과:

- `/tmp/d810-live-v21.meta`가 0바이트가 됐다.
- WebSocket은 `frameId`를 알 수 없었다.
- 같은 크기의 JPEG가 새 프레임인지 구분되지 않았다.
- 파일 크기와 앞·뒤 바이트를 비교하는 추측 기반 fallback이 동작했다.
- 실제 프레임은 생산되어도 전달 계층에서 누락될 수 있었다.

수정 내용:

- `_capture_frame()`이 프레임과 메타데이터를 함께 반환하도록 수정했다.
- 메타데이터를 임시 파일에 기록한 뒤 원자적으로 교체했다.
- WebSocket이 `frameId`, `captureMs`, `cacheMs`, `totalMs`를 사용하도록 했다.

### 6.5 LIVE_START의 Device Busy 성공 오판

워밍업을 추가한 후에도 첫 프레임이 나오지 않는 테스트가 있었다. 로그를
PTP 응답까지 내리자 다음 순서가 보였다.

```text
LIVE_START(0x9201) → 0x2019 Device Busy
그런데 bridge는 liveView=true / Ready로 기록
GET_LIVE_VIEW_IMAGE(0x9203) → 0xA00B
이후 프레임 획득만 반복
```

이는 카메라가 라이브뷰를 시작하지 않은 것이 아니라, 시작 실패를 브리지가
성공으로 판정한 문제였다.

수정 내용:

- `0x2019`를 `RESP_DEVICE_BUSY`로 명시했다.
- Device Ready와 LIVE_START 응답 코드를 검사한다.
- `Device Busy`일 때 제한된 횟수로 재시도한다.
- 성공하지 못하면 `liveview_start_failed`로 종료한다.
- 실제 시작 성공 전에는 `live_view_active=true`로 표시하지 않는다.

### 6.6 프레임 사이 71–75ms 공백

메타데이터 계측 결과 카메라 캡처 자체는 23–29ms였고 캐시 기록은 2–3ms였다.
그런데 다음 프레임 시작까지 71–75ms의 공백이 있었다.

원인은 브리지 루프가 이미 단일 실행 루프인데도 매 프레임마다 다음 작업을
반복했기 때문이다.

```text
mkdir FRAME_CAPTURE_LOCK
mkdir COMMAND_ACTION_LOCK
PTP 캡처
파일 기록
rmdir COMMAND_ACTION_LOCK
rmdir FRAME_CAPTURE_LOCK
```

이 락은 여러 외부 프로세스가 동시에 카메라를 만질 때는 의미가 있지만,
라이브 프레임을 생산하는 브리지 자신의 단일 루프 안에서는 중복이었다.
특히 임베디드 환경에서 `mkdir/rmdir`를 셸 프로세스로 매번 실행하는 비용이
프레임 간격을 크게 늘렸다.

수정 내용:

- 라이브 백그라운드 캡처에 한해 프로세스 락을 생략했다.
- 브리지 이벤트 루프 자체의 직렬성은 유지했다.
- AF·SHOT 등 외부 명령 경로의 락 계약은 보존했다.

결과적으로 `requestGapMs`가 약 71–75ms에서 약 8ms로 감소했다.

## 7. 현재 라이브뷰 데이터 흐름

```text
카메라 PTP
  ↓
DdServerWire: LIVE_START / GET_LIVE_VIEW_IMAGE
  ↓
BridgeSession:_capture_frame(false, true)
  ↓
frameId + capture metrics 생성
  ↓
JPEG 및 meta 원자적 캐시 기록
  ↓
d810ws.lua가 최신 frameId 감시
  ↓
WebSocket: meta → binary JPEG
  ↓
UI 최신 프레임 슬롯
  ↓
렌더 중이면 이전 대기 프레임 폐기
  ↓
화면 표시
```

핵심 규칙은 카메라가 생산자이고, UI는 소비자라는 점이다.

UI가 프레임 1을 렌더링하는 동안 카메라가 프레임 2를 생산하면, UI는 프레임
2를 최신 슬롯에 넣는다. 프레임 1 렌더가 끝난 뒤 프레임 2를 표시한다.
중간에 프레임 하나가 폐기될 수 있지만, 오래된 프레임을 전부 쌓아 수백 ms의
지연을 만드는 것보다 연속 영상처럼 보이는 데 유리하다.

## 8. 관측계

### 8.1 세션 로그

각 명령 세션은 별도 로그를 갖는다.

- 세션 디렉터리 예: `/root/d810-sessions/125_session/`
- 브리지 로그: `bridge.log`
- WebSocket 로그: `ws.log`
- 공용 상태: `/tmp/d810-session-v21.state`
- 공용 모드: `/tmp/d810-session-v21.mode`

로그에는 다음을 남긴다.

- 명령 수신 시각과 명령명
- PTP 응답 코드
- 카메라 연결·세션 오픈 결과
- 라이브뷰 시작·정지 결과
- 프레임 캡처 실패와 오류 분류
- 복구 시도와 리페어 요청
- 세션 ID와 backend state

### 8.2 프레임 메타데이터

`/tmp/d810-live-v21.meta`는 단순한 상태 파일이 아니라 프레임 파이프라인의
계측 지점이다.

주요 필드:

- `frameId`: 생산 순번
- `startedAt`: 프레임 작업 시작
- `captureStartedAt`: PTP 캡처 시작
- `captureDoneAt`: 카메라 데이터 수신 완료
- `writeDoneAt`: 캐시 기록 완료
- `prepMs`: 준비 시간
- `captureMs`: 카메라 캡처 시간
- `cacheMs`: JPEG와 메타 기록 시간
- `totalMs`: 전체 처리 시간
- `requestGapMs`: 이전 프레임 이후 다음 프레임 시작까지의 간격
- `bytes`: JPEG 크기
- `cached`: 실제 신규 프레임인지 캐시 프레임인지

### 8.3 UI 지표

UI는 다음을 표시하거나 추적한다.

- FPS
- Latency
- Session Condition
- Camera 상태
- Battery
- 현재 명령과 처리 단계

UI의 `Ready`만으로 성공을 확정하지 않는다. 반드시 브리지 로그와 프레임
메타데이터를 함께 본다.

### 8.4 병목 판별 규칙

| 관측 결과 | 의심 구간 |
|---|---|
| `captureMs`가 큼 | 카메라·PTP·ddserver |
| `requestGapMs`만 큼 | 브리지 루프·락·대기·중복 워커 |
| `cacheMs`가 큼 | 파일 기록·원자적 교체·스토리지 |
| frameId는 증가하나 UI FPS가 낮음 | WebSocket·디코드·렌더 |
| meta가 0바이트 | 프레임/메타 반환 계약 또는 기록 오류 |
| `Device Busy` 후 Ready | 시작 응답 판정 오류 가능성 |
| 리페어 파일 생성 | 생산자 실패 또는 세션 모드 불일치 |
| frame-refresh가 실행 중 | 단일 생산자 규칙 위반 |

## 9. 리페어 모듈 운영 원칙

리페어 모듈은 “문제가 생겼으니 일단 재시작”하는 모듈이 아니다.
관찰된 사실을 근거로 최소 범위의 복구를 수행해야 한다.

### 9.1 리페어 입력

- 브리지 프로세스 생존 여부
- WebSocket 프로세스 생존 여부
- USB/PTP 세션 상태
- `lastError`
- 프레임 실패 연속 횟수
- `SESSION_REPAIR_REQUEST`
- 세션 모드와 라이브 요청 파일의 일치 여부
- 프레임 메타의 마지막 갱신 시각

### 9.2 리페어 순서

```text
관찰
  ↓
단순 stale 파일/프로세스 여부 확인
  ↓
현재 브리지 상태 재조회
  ↓
카메라 명령 큐가 비었는지 확인
  ↓
라이브 시작/정지 상태 재검증
  ↓
필요할 때만 라이브뷰 재시작
  ↓
그래도 실패하면 연결 복구
  ↓
최후에만 브리지·세션 재기동
```

### 9.3 금지 사항

- UI의 모든 timeout을 리페어 원인으로 해석하지 않는다.
- 프레임이 잠시 늦다고 세션을 바로 교체하지 않는다.
- 라이브뷰 실패 시 별도 PTP 워커를 무조건 만들지 않는다.
- `Device Busy`를 `Ready`로 덮어쓰지 않는다.
- 이전 세션의 stale 플래그를 새 세션의 원인으로 사용하지 않는다.

## 10. 기능 정상화 기준

### AF

- `Ready` 상태에서 AF를 누를 수 있어야 한다.
- 실제 PTP AF 응답을 확인해야 한다.
- 카메라가 바쁘면 `Device Busy` 또는 `AF 불가`로 구분한다.
- AF 종료 후 카메라 락과 임시 상태가 정리되어야 한다.
- 라이브 프레임 루프와 충돌하지 않아야 한다.

### SHOT

- 라이브뷰 생산과 같은 카메라 큐에서 직렬화한다.
- 촬영 후 still JPEG 경로와 live JPEG 경로를 혼동하지 않는다.
- 촬영 완료 후 라이브뷰가 계속되거나 정책에 따라 명확히 정지되어야 한다.
- 촬영 실패가 라이브 세션 전체를 불필요하게 재시작하지 않아야 한다.

### LIVE

- LIVE_START 성공 전에는 UI를 최종 Ready로 확정하지 않는다.
- `Device Busy`는 제한 재시도 후 명확한 실패로 남긴다.
- 라이브 세션은 고정된 정체성을 유지한다.
- 브리지만 프레임 생산자가 된다.
- UI는 최신 프레임을 소비한다.

### STOP

- 라이브 생산을 멈춘다.
- WebSocket 연결을 닫는다.
- 라이브 요청 플래그와 stale worker를 정리한다.
- 명령 세션은 Ready로 돌아간다.

### 새로고침·하드 리셋

- 새 명령 세션 번호를 발급한다.
- 카메라에 남은 명령 큐와 임시 락을 정리한다.
- 리페어 플래그를 이전 세션에서 가져오지 않는다.
- 이전 라이브 세션 파일·프레임 캐시·모드 파일을 정리한다.
- 새 라이브 세션은 새 명령 세션이 Ready가 된 뒤 명시적으로 시작한다.
- UI가 이전 프레임과 새 세션 상태를 혼합하지 않는다.

2026-07-19 확인 결과:

- 오팔 `0716-1.html`과 로컬 파일 MD5가 동일했다.
- 정적 HTML 응답은 `no-store`, `no-cache`, `must-revalidate`였다.
- 따라서 기준 URL을 사용하면 오래된 브라우저 캐시가 남을 가능성은 낮다.

## 12. 현재 구현에 고정된 핵심 결정

1. 카메라별 PTP 작업은 단일 실행 경로에서 직렬화한다.
2. 라이브뷰는 고정된 라이브 세션 정체성을 사용한다.
3. 명령 세션 번호는 새로고침과 하드 리셋 시 새로 발급한다.
4. 브리지가 라이브 프레임의 유일한 생산자다.
5. WebSocket은 생산자가 아니라 전달자다.
6. UI fallback은 별도 카메라 캡처 워커를 만들지 않는다.
7. 프레임과 메타데이터는 함께 반환하고 원자적으로 기록한다.
8. `frameId`가 프레임의 신선도를 판정한다.
9. UI는 최신 프레임을 빠르게 버퍼링하고 오래된 프레임을 쌓지 않는다.
10. 실제 PTP 응답 코드를 상태 표시보다 우선한다.
11. 리페어는 관찰된 증거가 있을 때만 단계적으로 개입한다.
12. 성능 개선 전후에는 카메라·브리지·캐시·WebSocket·UI를 각각 측정한다.

## 13. 추가 아이디어와 보류 항목

### 13.1 프레임 파이프라인

- 파일 캐시를 유지하되, 장기적으로는 브리지에서 WebSocket으로 직접 전달하는
  경로를 재검토할 수 있다.
- 직접 전달을 다시 도입할 경우, 소켓 write가 브리지의 PTP 루프를 막지 않는
  비동기 송신 큐가 먼저 필요하다.
- 현재처럼 안정적인 파일 캐시 경로를 기준선으로 삼고 직접 스트림은 별도
  실험 플래그로 분리한다.

### 13.2 관측성

- 세션별 프레임 FPS 요약을 자동으로 남긴다.
- `captureMs`, `requestGapMs`, `cacheMs`, `uiLatency`의 p50/p95를 기록한다.
- 리페어 전후의 상태 변화를 하나의 이벤트 ID로 연결한다.
- UI에 빌드 식별자와 배포 시각을 표시해 구버전 접속을 즉시 구분한다.

### 13.3 명령 큐

- AF·SHOT·LIVE_STOP의 우선순위를 명시적인 큐 정책으로 관리한다.
- 같은 종류의 중복 상태 조회는 합친다.
- 사용자가 요청하지 않은 LIVE_START나 FRAME_STORE는 추적 가능한 이벤트로
  남긴다.

### 13.4 리페어 안전성

- 반복 실패 시 무한 재시작하지 않도록 재시작 예산을 둔다.
- 같은 오류가 일정 시간 반복될 때만 세션 교체를 허용한다.
- 카메라 배터리 부족, USB 분리, Device Busy, PTP 세션 손실을 각각 다른
  복구 정책으로 분리한다.

## 16. 최종 운영 문장

이 시스템의 목표는 모든 프레임을 억지로 보존하는 것이 아니다.
카메라가 생산한 최신 프레임이 안정적으로 흐르고, 사용자의 명령이 카메라에
정확히 도달하고, 문제가 생겼을 때 어느 구간에서 발생했는지 증거를 남기며,
필요한 만큼만 복구하는 것이다.

라이브뷰, 기능 정상화, 관측계, 리페어 모듈, 문제 발견과 해결 과정은 서로
분리된 기능이 아니라 Semi OS가 지켜야 할 하나의 운영 사이클이다.
